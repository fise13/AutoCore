# Руководство по дизайну AutoCore

## 🎯 Главный принцип: "Не нагружать пользователя"

Пользователь должен **думать о своих данных**, а не о том, как работает приложение.

---

## 📐 Основные принципы дизайна

### 1. **Один экран — одна задача**

❌ **Плохо:**
- Много действий на одном экране
- Перегруженный интерфейс
- Непонятно, что делать дальше

✅ **Хорошо:**
- Четкая последовательность шагов
- Каждый экран решает одну задачу
- Понятно, что делать на каждом шаге

**Пример:** Мастер импорта разбит на 4 четких шага, каждый со своей целью.

---

### 2. **Показывать, а не скрывать**

❌ **Плохо:**
- Скрытые меню
- Непонятные иконки
- Нужно угадывать, где что находится

✅ **Хорошо:**
- Все важное видно сразу
- Понятные названия вместо иконок
- Логичная группировка элементов

**Пример:** 
- Кнопки в тулбаре имеют текст: "Импорт Excel", "Экспорт Excel", "Добавить мотор"
- Не просто иконки, а понятные действия

---

### 3. **Предсказуемость**

Пользователь должен понимать, что произойдет после действия.

✅ **Хорошо:**
- Кнопка "Продать" → мотор становится проданным
- Кнопка "Импортировать" → данные сохраняются
- Кнопка "Отмена" → ничего не сохраняется

❌ **Плохо:**
- Непонятные последствия действий
- Неожиданное поведение
- Действия без подтверждения

---

### 4. **Обратная связь**

Пользователь должен видеть результат своих действий.

✅ **Хорошо:**
- Прогресс-бар при импорте
- Сообщение "Импортировано моторов: 150"
- Визуальное изменение статуса (проданный мотор выделен)

❌ **Плохо:**
- Действие выполняется, но непонятно, что происходит
- Нет индикации прогресса
- Непонятно, успешно ли выполнено действие

---

### 5. **Минимум кликов**

Важные действия должны быть доступны быстро.

✅ **Хорошо:**
- Основные действия в тулбаре (1 клик)
- Горячие клавиши для частых операций
- Контекстные действия в таблице

❌ **Плохо:**
- Действие требует 5+ кликов
- Нужно искать в меню
- Длинная цепочка действий

---

## 🎨 Визуальный дизайн

### Цветовая схема

**Принцип:** Использовать цвета осознанно, не для красоты.

- **Синий** — основные действия (кнопки "Далее", "Импортировать")
- **Серый** — проданные моторы (визуально отличаются)
- **Зеленый** — успешные операции, автоматически определенные значения
- **Красный** — ошибки, обязательные поля

**Не использовать:**
- Яркие цвета "для красоты"
- Слишком много разных цветов
- Цвета без смысла

---

### Типографика

**Иерархия:**
1. **Заголовки** — `.title2`, `.title3` (важные разделы)
2. **Подзаголовки** — `.headline` (названия листов, брендов)
3. **Основной текст** — `.body` (обычный текст)
4. **Вспомогательный** — `.caption`, `.secondary` (подсказки, метаданные)

**Принцип:** Размер шрифта должен отражать важность информации.

---

### Пробелы и отступы

**Принцип:** Группировать связанные элементы, разделять разные.

✅ **Хорошо:**
- Связанные элементы близко друг к другу
- Разные группы разделены отступами
- Достаточно "воздуха" для читаемости

❌ **Плохо:**
- Все элементы в кучу
- Нет визуальной группировки
- Слишком тесно или слишком просторно

---

### Иконки

**Принцип:** Иконки должны быть понятными или заменены текстом.

✅ **Хорошо:**
- Иконка + текст (например: 🔧 "Все моторы")
- Понятные системные иконки (checkmark, xmark)
- Иконки для визуального разделения категорий

❌ **Плохо:**
- Непонятные иконки без подписей
- Иконки, которые можно спутать
- Иконки "для красоты" без смысла

---

## 🔄 Интерактивность

### Состояния элементов

Каждый элемент должен иметь четкие состояния:

1. **Обычное** — элемент доступен
2. **Наведение** — видно, что элемент интерактивный
3. **Нажатие** — визуальная обратная связь
4. **Отключено** — серый, недоступен (с объяснением почему)

**Пример:** Кнопка "Далее" отключена, если не назначен обязательный `serial_code`.

---

### Валидация

**Принцип:** Показывать ошибки сразу, понятно и конструктивно.

✅ **Хорошо:**
- Ошибка рядом с полем
- Понятное сообщение: "Необходимо назначить колонку 'НОМЕР ДВИГАТЕЛЯ'"
- Кнопка недоступна, пока есть ошибки

❌ **Плохо:**
- Ошибка только после отправки
- Непонятное сообщение: "Ошибка валидации"
- Можно отправить форму с ошибками

---

### Загрузка и ожидание

**Принцип:** Пользователь должен понимать, что происходит.

✅ **Хорошо:**
- Прогресс-бар: "Импорт: 5 из 10"
- Индикатор загрузки при длительных операциях
- Сообщение о результате: "Импортировано моторов: 150"

❌ **Плохо:**
- Приложение "зависло" (нет индикации)
- Непонятно, сколько ждать
- Нет обратной связи

---

## 📱 Структура экранов

### Главный экран

**Принцип:** Три колонки для разных задач.

```
┌─────────────┬──────────────────┬─────────────┐
│   Sidebar   │   Motor List     │   Detail    │
│             │                  │             │
│ Навигация   │  Фильтры +       │  Детали     │
│ по данным   │  Таблица         │  выбранного │
│             │                  │  мотора     │
└─────────────┴──────────────────┴─────────────┘
```

**Почему так:**
- Боковая панель — для навигации (не меняется часто)
- Центр — основная работа (таблица моторов)
- Правая панель — детали (контекстная информация)

---

### Мастер импорта

**Принцип:** Пошаговый процесс с четкой навигацией.

```
┌─────────────────────────────────────┐
│  Заголовок: "Импорт Excel"          │
├─────────────────────────────────────┤
│                                     │
│  Контент текущего шага              │
│                                     │
├─────────────────────────────────────┤
│  [Отмена]  [Назад]  [Далее] →       │
└─────────────────────────────────────┘
```

**Элементы:**
- Заголовок показывает, на каком шаге находимся
- Контент — только для текущего шага
- Кнопки навигации всегда внизу
- "Далее" недоступна, пока шаг не завершен

---

### Настройка колонок

**Принцип:** Показывать максимум информации, минимум действий.

Для каждой колонки показываем:
- ✅ Букву колонки (A, B, C...)
- ✅ Заголовок (если есть)
- ✅ Preview значений (первые 3-5 строк)
- ✅ Dropdown для выбора назначения

**Почему preview важен:**
- Пользователь видит данные
- Понимает, что в колонке
- Может принять правильное решение

---

## 🎯 Паттерны взаимодействия

### 1. **Прогрессивное раскрытие**

Не показывать все сразу. Раскрывать по мере необходимости.

**Пример:**
- Основной список — основные поля
- Детали мотора — все поля + редактирование
- Расширенные настройки — только для продвинутых пользователей

---

### 2. **Контекстные действия**

Действия должны быть там, где они нужны.

**Пример:**
- Кнопка "Продать" в таблице моторов — прямо там, где мотор
- Кнопка "Вернуть" только для проданных моторов
- Редактирование в правой панели, когда мотор выбран

---

### 3. **Пустые состояния**

Пустой экран должен объяснять, что делать.

✅ **Хорошо:**
```
┌─────────────────────┐
│   🔧                │
│                      │
│ Моторов пока нет     │
│                      │
│ Добавьте первый      │
│ мотор, чтобы начать  │
│                      │
│ [Добавить мотор]     │
└─────────────────────┘
```

❌ **Плохо:**
```
┌─────────────────────┐
│                     │
│   (пусто)           │
│                     │
└─────────────────────┘
```

---

### 4. **Подтверждение опасных действий**

Действия, которые нельзя отменить, требуют подтверждения.

**Пример:**
- Удаление данных — подтверждение
- Очистка всей БД — подтверждение
- Импорт (можно отменить через Undo, но лучше предупредить)

---

## 🚫 Что НЕ делать

### ❌ Не перегружать информацией

**Плохо:**
- Много текста на экране
- Все опции видны сразу
- Технические детали в интерфейсе

**Хорошо:**
- Только необходимое
- Дополнительная информация по запросу
- Технические детали скрыты

---

### ❌ Не использовать жаргон

**Плохо:**
- "Upsert", "Normalize", "Transaction"
- Технические термины
- Аббревиатуры без расшифровки

**Хорошо:**
- "Сохранить", "Обновить", "Импортировать"
- Понятные слова
- Объяснения простым языком

---

### ❌ Не делать предположений

**Плохо:**
- Автоматически определять формат
- Предполагать, что пользователь хочет
- Скрывать важные решения

**Хорошо:**
- Показывать варианты
- Давать выбор
- Пользователь решает сам

---

### ❌ Не скрывать ошибки

**Плохо:**
- Тихая ошибка в консоли
- Непонятное сообщение
- Ошибка без решения

**Хорошо:**
- Понятное сообщение пользователю
- Объяснение, что не так
- Подсказка, как исправить

---

## ✅ Чек-лист для проверки дизайна

Перед добавлением нового экрана/функции проверь:

- [ ] Понятно ли, что делать на экране?
- [ ] Видны ли все важные элементы?
- [ ] Есть ли обратная связь на действия?
- [ ] Понятны ли ошибки и как их исправить?
- [ ] Не перегружен ли интерфейс?
- [ ] Логична ли последовательность действий?
- [ ] Работает ли навигация интуитивно?
- [ ] Нет ли технического жаргона?
- [ ] Достаточно ли "воздуха" между элементами?
- [ ] Соответствует ли дизайн остальному приложению?

## 🎨 Примеры хорошего дизайна в AutoCore

### 1. **Фильтрация моторов**

✅ **Хорошо:**
- Сегментированный контрол: Все / В наличии / Продан
- Понятные названия
- Визуально разделены
- Результат виден сразу

### 2. **Настройка колонок**

✅ **Хорошо:**
- Каждая колонка в отдельной строке
- Видно букву, заголовок, preview
- Dropdown для выбора
- Обязательные поля помечены

### 3. **Preview перед импортом**

✅ **Хорошо:**
- Показывает, как данные будут сохранены
- Таблица с реальными данными
- Статистика (сколько моторов, брендов)
- Можно проверить перед импортом

### 4. **Пустые состояния**

✅ **Хорошо:**
- Иконка для визуального понимания
- Понятный текст
- Подсказка, что делать
- Кнопка действия (если нужно)

## 📊 Метрики хорошего дизайна

Хороший дизайн можно измерить:

1. **Время до первого действия**
   - Пользователь понимает, что делать, за < 5 секунд

2. **Количество ошибок**
   - Пользователь не делает ошибок из-за непонятного интерфейса

3. **Количество кликов до цели**
   - Важные действия доступны за 1-2 клика

4. **Время выполнения задачи**
   - Импорт Excel занимает разумное время с понятными шагами

5. **Удовлетворенность**
   - Пользователь не чувствует себя потерянным
   - Понятно, что происходит на каждом шаге

---

## 🎯 Итоговые принципы

### 1. **Простота важнее красоты**
Красивый, но непонятный интерфейс хуже простого и понятного.

### 2. **Пользователь всегда прав**
Если пользователь не понимает — это проблема дизайна, а не пользователя.

### 3. **Меньше — лучше**
Лучше убрать лишнее, чем добавить ненужное.

### 4. **Контекст важен**
Показывать только то, что нужно в данный момент.

### 5. **Обратная связь обязательна**
Пользователь должен видеть результат каждого действия.

## 💡 Запомнить

> **"Хороший дизайн — это когда пользователь думает о своих данных, а не о том, как работает приложение."**

Если пользователь задается вопросом "Как это работает?" — дизайн можно улучшить.

Если пользователь сразу понимает, что делать — дизайн хороший.

---

## 🔄 Итерации

Дизайн не должен быть статичным. Если пользователи:
- Часто ошибаются в одном месте → упростить
- Спрашивают, как что-то сделать → сделать понятнее
- Пропускают важные шаги → сделать заметнее

**Принцип:** Дизайн улучшается на основе использования, а не предположений.
